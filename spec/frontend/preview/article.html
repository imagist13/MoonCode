用 DDD 构建可维护的 Go 后端

Moon · 2026 年 7 月 25 日 · 8 分钟阅读 · 后端

DDD（Domain-Driven Design，领域驱动设计）强调把业务逻辑放在软件的核心位置。在 Go 项目中落地时，我们通常将代码划分为四层：Interface、Application、Domain、Infrastructure，依赖单向流动，职责清晰。

一、分层与职责

每一层只关心自己该关心的事：Interface 处理 HTTP、Application 编排用例、Domain 表达业务规则、Infrastructure 对接外部世界。

// domain/article/entity.go
type Article struct {
    ID       uint
    Title    string
    Slug     string
    Content  string
    AuthorID uint
}
好架构不是让代码变多，而是让每一次改动都能落在明确的位置。

二、仓储接口

Domain 层只定义 Repository 接口，具体实现放在 Infrastructure 层，这样业务规则与存储细节解耦，测试只需要 mock 掉接口即可。

type Repository interface {
    Save(a *Article) error
    FindBySlug(slug string) (*Article, error)
    List(offset, limit int) ([]*Article, error)
}

三、依赖注入与启动链

在 main.go 中把各层组合起来：读取配置 → 初始化 DB / Redis → 注入仓储实现 → 注册 Handler。启动链路清晰，测试也变得非常容易。

四、常见的错误认识

DDD 并不等于「每个 struct 都要有 Value Object」。对一个中小型项目而言，把握好「依赖方向」和「层职责」比追求纯度更重要。
